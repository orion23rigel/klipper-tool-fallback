## Summary

This is a deep cross-file review of the v1.2 milestone (Phases 8-12), covering the tool fallback extension's state management, user commands, undefined tool detection, prompt flow, and fallback integration. The codebase is remarkably well-structured with frozen dataclasses, atomic file writes, and a comprehensive test suite. However, several critical and warning-level issues were identified across cross-module boundaries, state mutation paths, and error handling chains.

## Critical Issues

### CR-01: `_handle_guarded_resume` clears checkpoint before verifying resume success — state corruption on resume failure

**File:** `klippy/extras/tool_fallback.py:1507`

**Issue:** In `_handle_guarded_resume`, the workflow checkpoint is cleared (`self._workflow_checkpoint = None`) at line 1507 *before* the resume gcode is executed (lines 1508-1521). If the resume fails, the code attempts to re-create a blocked checkpoint, but the original `checkpoint` variable still holds the `heating_timeout` state — however, the checkpoint was already cleared from `self._workflow_checkpoint`. The re-creation at line 1516 creates a new `blocked` checkpoint, but this is assigned to a local variable and passed to `_block_workflow`. While `_block_workflow` does set `self._workflow_checkpoint = blocked`, the sequence is fragile: if `_block_workflow` itself fails (e.g., throws), the checkpoint is permanently lost.

More importantly, the flow at lines 1507-1521 is:
1. Clear checkpoint (line 1507)
2. Try to resume (line 1512)
3. On failure, create blocked checkpoint and call `_block_workflow` (lines 1516-1521)
4. On success, call `_finalize_fallback_success(checkpoint)` (line 1522)

Step 3 is correct because `_block_workflow` sets `self._workflow_checkpoint`. But step 4 uses the *original* `checkpoint` variable (which is the `heating_timeout` checkpoint that was already cleared). This is a logical error — the finalized event will reference a checkpoint whose stage is `heating_timeout`, not `blocked`. The notification will say the fallback succeeded, but the checkpoint it references was already cleared and never reached a success stage.

**Fix:** Save the checkpoint stage before clearing, and use a proper success-stage checkpoint for finalization:

```python
# Before line 1507:
completed = self._workflow_checkpoint
self._workflow_checkpoint = None
if checkpoint.pause_owned:
    try:
        self.gcode.run_script_from_command(
            self.config.global_config.resume_gcode)
    except Exception as error:
        blocked = replace(checkpoint, stage="blocked",
                          failure_reason="Resume after fallback failed: %s" % (error,))
        self._block_workflow(blocked,
                             "Resume after fallback failed: %s" % (error,),
                             "RESUME_FAILED")
        return None
success_checkpoint = replace(completed, stage="heating_timeout", failure_reason=None)
self._finalize_fallback_success(success_checkpoint)
```

### CR-02: `_handle_undefined_tool_prompt` uses a busy-wait loop that blocks the Klipper reactor

**File:** `klippy/extras/tool_fallback.py:1116-1129`

**Issue:** The undefined-tool prompt uses a `while True` loop with `reactor.advance(0.1)` at line 1129. While this does advance the reactor (allowing timer callbacks to fire), it is a **synchronous blocking loop** that holds the G-code command thread for up to `undefined_tool_timeout` (default 300 seconds). During this time:

1. No other G-code commands can be processed
2. The Klipper event loop is effectively hijacked
3. If a user sends another command during the prompt, it will be queued but not processed until the prompt completes (either by user response or timeout)

This is particularly dangerous in a 3D printer context where the user might need to respond within the timeout window. If the user's response (via `DEFINE_TOOL_BACKUP`) comes from a separate G-code invocation, it will be queued *behind* the current command that's stuck in the loop. The `DEFINE_TOOL_BACKUP` handler clears `self._undefined_tool_pending`, which the loop checks — but the loop only checks the sentinel at line 1120, which happens *after* the full 0.1-second `reactor.advance()` call completes.

This creates a worst-case latency of 100ms between user response and prompt completion, which is acceptable, but the fundamental design of blocking the entire reactor for potentially 5 minutes is a safety concern.

**Fix:** Use Klipper's timer-based event model instead of a busy-wait loop. Register a one-shot timer that checks the sentinel and re-schedules itself if still pending.

```python
def _undefined_tool_prompt_timer(self, eventtime):
    if self._undefined_tool_pending is None:
        self._undefined_tool_prompt_complete()
        return self.printer.get_reactor().NEVER
    if eventtime >= self._undefined_tool_timeout_deadline:
        self._handle_undefined_tool_timeout(self._undefined_tool_pending)
        return self.printer.get_reactor().NEVER
    return eventtime + 0.1

# In _handle_undefined_tool_prompt, replace the while loop with:
self._undefined_tool_timeout_deadline = timeout_deadline
reactor.update_timer(
    self._undefined_tool_prompt_timer_handle, timeout_deadline)
```

## Warnings

### WR-01: `_resolve_backup_with_rescan` creates a temporary `FallbackState` that may diverge from canonical state

**File:** `klippy/extras/tool_fallback.py:1549-1560`

**Issue:** When a user-defined backup exists, `_resolve_backup_with_rescan` creates a temporary `effective_state` with a modified `ToolState` for the failed tool (line 1550-1560). This temporary state is used only for `resolve_backup_graph()`. However, the temporary state's `ToolState` copies `user_defined_backup` from the original (line 1555), which means the user_defined_backup field is both the source of the effective backup list *and* stored on the tool itself. This is redundant and confusing — if `user_defined_backup` is used to derive `effective_backups`, it should not also be persisted as part of the tool state in the same way.

More critically, the temporary state is created from `state.tools` (a `MappingProxyType`), then `dict(state.tools)` is called to create a mutable copy (line 1557). The resulting `effective_state` is passed to `resolve_backup_graph`, but if the graph traversal modifies the state (it shouldn't, since it's read-only), changes would be lost.

**Fix:** Add a comment clarifying that `effective_state` is read-only and temporary. Consider extracting the effective backup list as a parameter to `resolve_backup_graph` rather than constructing a temporary state.

### WR-02: `_confirmed_runout` calls `_on_confirmed_runout` with the original checkpoint, but the checkpoint may have advanced

**File:** `klippy/extras/tool_fallback.py:1202-1207`

**Issue:** `_confirmed_runout` advances the checkpoint to `confirmed_runout` stage (line 1203-1204), then calls `_on_confirmed_runout(advanced)` at line 1207. However, `_on_confirmed_runout` receives `advanced` as the checkpoint parameter, but inside `_on_confirmed_runout` (line 1235), `_capture_and_shutdown_source(checkpoint)` is called with this checkpoint. `_capture_and_shutdown_source` (line 756-788) creates a new checkpoint with `stage="source_shutdown"` and assigns it to `self._workflow_checkpoint`. If `_capture_and_shutdown_source` returns `None` (because the stage doesn't match), `_on_confirmed_runout` silently returns without any error indication.

The real problem: `_confirmed_runout` calls `_on_confirmed_runout(advanced)`, but `_on_confirmed_runout` doesn't use the `checkpoint` parameter for validation — it passes it directly to `_capture_and_shutdown_source`. If `_checkpoint_matches` fails inside `_capture_and_shutdown_source` (it doesn't directly, but the stage advancement logic may not match), the workflow could be silently abandoned.

**Fix:** Add explicit validation in `_on_confirmed_runout` that the checkpoint stage matches expected values before proceeding.

### WR-03: `_begin_pending_runout` silently ignores runout events when a workflow is active

**File:** `klippy/extras/tool_fallback.py:1026-1029`

**Issue:** When a workflow checkpoint exists and is not in the `debouncing` stage for the same tool, `_begin_pending_runout` logs a message and returns without taking any action. This means that if a user triggers `TOOL_FALLBACK_RUNOUT` for a different tool while an automatic fallback workflow is active for another tool, the event is silently dropped. While this is intentional (to prevent conflicting workflows), the user has no way to know their runout event was ignored beyond the info message.

This becomes a problem if the user's runout event is critical (e.g., they just loaded new filament and need the system to know). The info message "Ignoring runout for X because another tool fallback workflow is active" goes to the console, but if the user is not actively monitoring, they may not notice.

**Fix:** Consider queuing the runout event for processing after the current workflow completes, similar to how backup operations are queued.

### WR-04: `reconcile` preserves `user_defined_backup` from old state even when the tool is removed from config

**File:** `klippy/extras/tool_fallback_state.py:165-194`

**Issue:** In `FallbackState.reconcile()`, when a tool is removed from the configuration, its entry is simply not added to the new `tool_states` dict (line 168-172). However, `filtered_backups` (line 188-192) correctly filters out user-defined backups for tools not in `configured_names`. But the `mappings` dict (line 184-187) sets `mappings[name] = name` for all configured tools. If a tool was previously mapped to a different physical tool and that physical tool was removed from config, the mapping would be reset to identity. This is correct behavior, but the `reconcile` method doesn't handle the case where a tool's `user_defined_backup` references a tool that has been removed from configuration — it only filters the `user_defined_backups` dict by logical tool, not by backup target.

Consider: T0 has `user_defined_backup = "T3"`, and T3 is removed from config. The `filtered_backups` dict (line 188-192) will keep `T0: T3` because T0 is still configured. But T3 no longer exists as a tool, so the backup reference is invalid.

**Fix:** Filter `user_defined_backups` by both logical tool AND backup target:

```python
filtered_backups = {
    logical: backup
    for logical, backup in self.user_defined_backups.items()
    if logical in configured_names
    and (backup is None or backup in configured_names)
}
```

### WR-05: `_cmd_resume_wrapper` re-entrancy guard uses `_resume_in_progress` but `_handle_guarded_resume` can throw

**File:** `klippy/extras/tool_fallback.py:1416-1441`

**Issue:** The re-entrancy guard at line 1425 checks `self._resume_in_progress` and delegates to `_resume_original` if set. However, the `finally` block at line 1441 sets `self._resume_in_progress = False`. If an exception is raised at line 1439 (`raise gcmd.error(str(error))`), the `finally` block still executes and clears the flag. This is correct.

But consider this scenario: `_cmd_resume_wrapper` is called, `_resume_in_progress` is True, and `_resume_original` exists. The code returns `_resume_original(gcmd)` at line 1427. The `finally` block still runs and sets `_resume_in_progress = False`. This is fine.

However, there's a subtle issue: if `_handle_guarded_resume` raises an exception (line 1437), the `finally` block clears `_resume_in_progress` at line 1441, and then the exception propagates. But the exception is caught at line 1438 and re-raised as `gcmd.error(str(error))`. The `finally` block runs *before* the exception is re-raised, so the flag is correctly cleared. This is actually correct behavior.

The real warning is that `_resume_in_progress` is a simple boolean flag that doesn't track *which* resume operation is in progress. If two RESUME commands arrive nearly simultaneously (before the first one completes), the second one will see `_resume_in_progress = True` and delegate to `_resume_original`. This could cause unexpected behavior if the original resume handler and the guarded resume handler interact in unexpected ways.

**Fix:** Consider using a generation counter or lock instead of a boolean flag for more robust re-entrancy protection.

### WR-06: `_select_and_conditionally_purge` may issue a second `_select_physical` call

**File:** `klippy/extras/tool_fallback.py:610-631`

**Issue:** `_select_and_conditionally_purge` calls `_select_physical(physical_tool)` at line 620. However, `_select_physical` (line 633-644) calls the physical handler directly (line 643: `handler(physical_gcmd)`). This means the physical tool's G-code handler is invoked. If the handler itself calls back into the tool fallback system (e.g., through a G-code script that triggers another fallback event), this could cause re-entrancy issues.

The method is called from `_route_logical` (line 606) and from `_on_confirmed_runout` (line 1273). In the latter case, the workflow is already in progress, so a re-entrant call could corrupt the checkpoint state.

**Fix:** Add a re-entrancy guard in `_select_physical` or document that physical handlers must not trigger tool fallback events.

## Info

### IN-01: `resolve_backup_graph` doesn't validate that `failed_tool` exists in `state.tools`

**File:** `klippy/extras/tool_fallback.py:141`

**Issue:** `resolve_backup_graph` immediately accesses `state.tools[failed_tool].backups` at line 141 without checking if `failed_tool` exists. If called with an invalid tool name, this will raise a `KeyError` rather than a `StateValidationError`. While the caller (`_resolve_backup_with_rescan`) always passes a valid tool name, this lack of defensive validation at the function boundary makes the function harder to test and reuse.

**Fix:** Add a guard at the start of `resolve_backup_graph`:
```python
if failed_tool not in state.tools:
    raise KeyError("Unknown failed tool: %s" % failed_tool)
```

### IN-02: `SensorRuntime` dataclass uses `object` type for many fields

**File:** `klippy/extras/tool_fallback.py:27-42`

**Issue:** The `SensorRuntime` dataclass uses `object` as the type annotation for `name`, `sensor`, `enabled`, `detected`, `confirmed_detected`, `debounce_target`, `debounce_deadline`, `debounce_origin`, and `poll_timer`. While this is technically correct (these fields can be `None` or their actual type), using `object` instead of `Optional[ActualType]` makes the code harder to understand and debug. Type checkers cannot provide meaningful help with `object` types.

**Fix:** Use `Optional[str]`, `Optional[bool]`, `Optional[float]`, `Optional[int]`, and `Optional[Timer]` (or whatever the actual Klipper timer type is) for better type safety.

### IN-03: Test `test_undefined_tool_user_response_resumes` doesn't verify the checkpoint is cleared

**File:** `tests/test_tool_fallback_extension.py:608-638`

**Issue:** The test manually sets up the prompt flow state and calls `DEFINE_TOOL_BACKUP`, then verifies the sentinel is cleared and the state is updated. However, it doesn't verify that `_workflow_checkpoint` is cleared after the user response. In the actual `_handle_undefined_tool_prompt` flow, the checkpoint is cleared at line 1134. But when the user calls `DEFINE_TOOL_BACKUP` directly (as in this test), the checkpoint is NOT cleared by the command handler — only the sentinel is cleared. The test doesn't catch this because it doesn't check `_workflow_checkpoint` after the user response.

**Fix:** Add an assertion: `assert extension._workflow_checkpoint is not None` (since `DEFINE_TOOL_BACKUP` doesn't clear it) or update the test to verify the checkpoint is advanced to a completion stage.

### IN-04: `_parse_backup_list` doesn't validate tool name format

**File:** `klippy/extras/tool_fallback.py:1715-1739`

**Issue:** `_parse_backup_list` validates that backup names are in `self.config.tools` (line 1726), which implicitly validates they are configured. However, it doesn't validate that the backup names match the `TOOL_NAME_RE` pattern. If a user configures a tool with a non-canonical name (which `parse_tool_config` should prevent), the backup list would accept it. While this is unlikely in practice because `parse_tool_config` normalizes names, the validation chain is incomplete.

**Fix:** Add `TOOL_NAME_RE.fullmatch(item)` validation in `_parse_backup_list` for defense-in-depth.

### State Mutation Paths
1. **Initialization**: `_handle_ready` → `store.load_reconciled` → `state.reconcile` → `store.save`
2. **User commands**: G-code handler → `_persist_state` → `store.save`
3. **Sensor debounce**: `_sensor_debounce_handler` → `_build_sensor_filament_candidate` → `_persist_state`
4. **Runout confirmation**: `_confirmed_runout` → `_on_confirmed_runout` → `_persist_state`
5. **Fallback workflow**: `_on_confirmed_runout` → `state.with_mapping` → `_persist_state`

All mutation paths go through `_persist_state`, which calls `store.save`. The `StateStore.save` method checks for equality with `_persisted_state` to avoid unnecessary writes. This is correct and efficient.

### Error Propagation
- Configuration errors during `finalize_configuration` are raised and caught in `_handle_ready`
- State load errors are caught and re-raised as path-specific `ConfigError`
- File system errors during persistence are caught in individual command handlers and raised as `gcmd.error`
- Notification failures are caught and logged but don't block the workflow

The error propagation is generally correct, with one gap: `_handle_guarded_resume` (CR-01).
